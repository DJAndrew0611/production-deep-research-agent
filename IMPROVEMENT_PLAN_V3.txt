结论：这次已经从“加几个治理概念”进展到“有明确工程骨架的 Agent 原型”。相比上一版，提升很明显；但证据闭环、差分回归、事实修订一致性这三块仍有关键断点。

新的判断：

- 作品集：8.5/10
- 大厂初级/中级 Agent 工程岗：够用，且能经受一定深挖
- 大厂中高级、生产型 Agent 岗：7/10，仍需补最后几个核心闭环
- 当前准确定位：**具备证据校验、版本化和运行治理能力的单机 Deep Research Agent 原型**

## 仍然存在的核心问题

### 1. 线上 Workflow 没有真正使用 EvidenceCorpus

这是当前最重要的问题。

`core/workflow.py` 虽然导入了：

```python
build_corpus_from_sources
```

但实际没有调用它。Stage 1、Stage 2 和最终 deterministic verification 都没有把真实搜索得到的 corpus 传入：

```python
evidence_ledger.recompute_all_statuses()
verify_claims_deterministically(evidence_ledger.claims)
```

而不是：

```python
evidence_ledger.recompute_all_statuses(corpus=corpus)
verify_claims_deterministically(evidence_ledger.claims, corpus=corpus)
```

因此：

> Benchmark 中会检查“引用是否属于 corpus”，但线上真实运行时，状态机仍可能接受模型给出的任意有效 URL。

也就是说，Citation Validator 已经写出来了，但最关键的线上调用链还没有真正接通。

优先修复方式：

1. 每次 Research/Gap Search 后用 `build_corpus_from_sources()` 构建或更新 corpus；
2. 将 corpus 保存到 session/revision；
3. 所有 `recompute_all_statuses()` 都传入 corpus；
4. 所有 `verify_claims_deterministically()` 都传入 corpus；
5. 缺口补查新增的 evidence 必须先写入 corpus，再参与状态计算。

### 2. Negative Transfer 仍是“模拟退化”，不是真实 candidate 回归

当前评测已经有 differential comparison，但 [evaluation/runner.py:134](E:/Agent项目/awesome-llm-apps-main/advanced_ai_agents/single_agent_apps/ai_deep_research_agent/evaluation/runner.py:134) 的逻辑仍然是：

- 复制 baseline 结果；
- 如果 candidate 包含危险关键词；
- 手动把 false corroboration 改成 0.5、gap recall 改成 0。

它并没有真的：

```text
baseline: memory=[]
candidate: memory=[candidate]
分别运行同一 workflow
比较每一个 case 的真实输出
```

所以当前的差分回归比之前好，但本质仍是“规则文本风险扫描 + 模拟退化”。

面试时不能说“已实现真实负迁移评测”，只能说：

> 已实现差分评测框架和高风险策略拦截；candidate 注入 workflow 的真实回归仍在完善。

### 3. Feedback Revision 仍未重新验证事实

版本记录已创建，但反馈修订路径仍主要是：

```text
LLM 生成 revised_report
↓
append_feedback_to_session
↓
复制旧 ledger snapshot
↓
verification_snapshot_json = None
```

见 [storage.py:295](E:/Agent项目/awesome-llm-apps-main/advanced_ai_agents/single_agent_apps/ai_deep_research_agent/storage.py:295)。

因此新 revision 虽然有版本号和父子关系，但若用户修改了：

- 日期；
- 数字；
- 事实结论；
- 引用；
- 发布状态；

新报告并没有自动重跑：

- evidence extraction；
- corpus validation；
- claim state machine；
- verification result。

所以目前实现的是“报告版本化”，但还不是“事实资产版本化”。

这是下一轮最值得优先修复的问题。

### 4. Verification Agent 仍然不输出结构化结果

目前结构化 `VerificationResult` 来自：

```python
verify_claims_deterministically(...)
```

这很好，因为最终结论不能直接被模型控制。

但 Verification Agent 自己仍被要求输出 Markdown 审计文本，而不是结构化 JSON。它的输出更多是“辅助说明”，不是可被解析和落库的逐 claim 验证结论。

更成熟的形态应该是：

```text
Verification Agent -> VerificationResult[]
↓
确定性规则复核
↓
更新 Claim 状态
↓
程序渲染 Markdown 审计报告
```

当前实现是：

```text
Verification Agent -> Markdown
确定性状态机 -> VerificationResult[]
最终报告 = 两者拼接
```

这并不错误，但模型验证能力没有真正进入结构化闭环。

### 5. Gap Search 仍使用关键词推断 stance

在 [core/workflow.py](E:/Agent项目/awesome-llm-apps-main/advanced_ai_agents/single_agent_apps/ai_deep_research_agent/core/workflow.py) 中，仍根据：

- 否定关键词；
- claim token overlap；
- URL 中是否出现 `blog/news/press`；

来判断支持还是反驳。

这是可以接受的第一版 heuristic，但它不能称为语义蕴含验证，也不能可靠判定一手来源。

至少要把逻辑升级成：

- evidence snippet 与 claim 的明确匹配；
- 日期/数字约束匹配；
- corpus 绑定；
- publisher/domain allowlist 或可配置规则；
- `is_first_party` 不能由 URL 子串推测；
- 对不确定结论默认 `neutral/unverified`。

### 6. Benchmark 仍主要验证“理想 Mock 输出”

Benchmark 已经使用真实 parser、corpus 和 citation validator，比之前好了很多。

但 [evaluation/mock_services.py](E:/Agent项目/awesome-llm-apps-main/advanced_ai_agents/single_agent_apps/ai_deep_research_agent/evaluation/mock_services.py) 中的 Mock LLM 依然生成：

- 正确 claim；
- 正确引用；
- 正确 snippet；
- 正确 stance；
- 正确 trap 标记。

所以它更接近：

> 验证系统能够正确处理理想输出。

还不充分验证：

> 系统是否能在模型输出错误日期、伪 URL、错误 stance、缺失 JSON、混入注入文本时拒绝错误结论。

虽然单元测试已经覆盖部分失败情况，但这些失败 fixture 应进入 `cases.jsonl` 和完整 workflow Benchmark，才是真正强的评测集。
